# 工作原则

生成并推进项目时遵守：

## 0. upsert → 询问 → 确认后再开工

安装或更新 skill 后先询问是否立即新建项目。用户明确同意（或之后主动要求开新项目）再做环境检测与脚手架；用户说先不或未同意则停住。

## 1. 环境先于要建的端，端先于业务

（在已确认开工之后）先确定本期要哪些端，再按 `environment-setup.md` 只保证这些端的工具可用，然后写入 `product/` 并只建这些端，再写功能。用不到的端不建。

## 2. 栈保持默认

默认 Vue3 + Ant Design Vue、Go（Gin + GORM）。MySQL、Redis、Elasticsearch 以及以后的基础设施都在 `/srv/docker/<组件>/` 共用；每个服务只用自己的库或命名空间。换栈需用户明确授权。

## 3. 前后台分离

`web`（用户侧网页+H5）与 `admin`（管理后台）分目录、分工程。

## 4. 必要产品信息进 `product/`

用户、目标、场景、范围、主路径、本期要哪些端写入 `product/README.md`。要做的每一页写 `product/<页面名>/结构草稿.json`，改页面先改这份草稿。不写 PRD，不写 HTML 原型。缺口收成一次选择：2～3 个方案并标明建议项；选定或按建议采用后写入，然后继续。同一件事不追问第二轮。项目约定写在根 README。

## 5. 一键能讲清怎么跑

README 只写已经存在的端：本机环境要求、本地怎么起、各目录职责一句话。写本项目实际用到的基础设施位置，以及自己的库或命名空间。有 `deploy` 时写本服务自己的 compose，里面不含基础设施。

## 6. 小步可演示

优先打通本期需要的最短路径（只要接口就先健康检查；要页面再接对应端），再铺功能。不预建用不到的端。

## 7. 改完即运行，并用浏览器自测

项目存在之后，每次写完代码都先重启到本次改动，再用浏览器自测。有页面就打开实际地址，按这次改的路径点击、输入、提交，并核对结构草稿。只有接口时打开该接口地址核对返回。失败先修再测。通过后才把地址和自测结果告诉用户。只改产品文档且还没有端时，说明暂无可访问地址。

## 8. 用 Git 做版本管理

项目根目录是 Git 仓库。新建时 `git init`、写 `.gitignore`、做首次提交；已有仓库则沿用。每次调整修改落地后提交一次。不推远程，除非用户要求。不改 git config，不改历史。密钥、`.env`、依赖目录和构建产物不入库。

## 9. 工具版本克制

已安装且可用 → 保持现状；缺失 → 装较新稳定版。
